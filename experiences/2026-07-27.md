## 4. Guide 业务摘要误报未包含 SPEC_LIMIT 规则表的根因修复
### 背景
- 用户在 Guide 自动生成业务实体与关系时，已经在业务说明文档明确写明 `PDX25_TAMS_SFR_SPEC_LIMIT` 是 SFR 的 `SPEC_LIMIT` 规则表，但后续生成的业务摘要仍返回：
  - `业务文档提及了 SPEC_LIMIT 规则表，但当前所选业务关系表中未包含对应规则表。`
- 排查发现这不是 LLM 自相矛盾，而是 Guide 前置摘要构造阶段的后端截断逻辑导致的误判。

### 改动文件列表
- `backend/app/services/ontology_guide_service.py`

### 具体改动
- 现有 `OntologyGuideService.generate()` 在读取已选业务关系表明细时，只会处理前 `GUIDE_TABLE_FETCH_LIMIT = 12` 张表：
  - `rule_summary`
  - `spec_limit_summary`
  - `business_summary`
  都基于这批明细计算。
- 当用户勾选的表超过 12 张时，即使 `PDX25_TAMS_SFR_SPEC_LIMIT` 已被选中，只要它没有落在前 12 张里，就不会进入：
  - `_build_selected_table_schema()`
  - `_build_rule_summary()`
  于是会被错误判断成“当前所选业务关系表中未包含对应规则表”。
- 本轮新增 `_prioritize_table_bindings_for_guide()`：
  - 优先保留业务文档中被明确点名的表
  - 其次优先显式标注为 `rule_catalog` 的表
  - 再次优先表名中带 `SPEC` / `LIMIT` 的规则表
- `generate()` 现在先对已选表做优先级排序，再截取前 12 张做明细分析；这样在表数较多时，`PDX25_TAMS_SFR_SPEC_LIMIT` 这类规则表会优先进入 `rule_summary` 和后续业务摘要。
- 同时增加日志：
  - `Guide selected tables prioritized`
  便于后续直接从服务端日志确认哪些表被纳入本轮前 12 张明细分析。

### 验证结果
- 执行：
  - `./.venv311/bin/python -m py_compile app/services/ontology_guide_service.py`
  - `npm run build`
- 结果：
  - 后端语法检查通过
  - 前端构建通过

### 结论
- 本问题的根因是 Guide 表明细分析前的“前 12 张表截断”与“未做规则表优先级提升”，不是大模型单纯理解错误。
- 修复后，即使用户勾选表较多，只要业务文档明确提到 `PDX25_TAMS_SFR_SPEC_LIMIT`，该规则表也会优先进入 Guide 摘要与后续本体/关系生成上下文。

## 6. Guide 全量选表后触发 53 万 tokens 上下文超限的修复
### 背景
- 删除 12 表硬限制后，用户在 Guide 中选择较多表时出现报错：
  - `当前模型 gpt-5.4 的可用输入预算约为 200000 tokens，本次请求预计输入约 533576 tokens，存在上下文超限风险。`
- 排查确认，这不是单纯业务文档过长，而是 `generate_ontology_design_document()` 之前仍把 `selected_table_schema` 的全量表字段明细直接传给 LLM。
- 也就是说：
  - 前置规则识别希望看到全部选表
  - 但高层设计文档生成不应该继续吃全量字段明细
  - 之前删除 12 表限制后，这一步就暴露出超大 prompt 问题

### 改动文件列表
- `backend/app/services/ontology_guide_service.py`

### 具体改动
- 保留全量 `selected_table_schema`，继续用于：
  - `_build_rule_summary()`
  - `business_summary`
  - `table_roles`
  - `source_role_bindings`
- 新增将 `llm_table_details` 转回 `llm_selected_table_schema` 的调用：
  - 基于现有 `_build_llm_table_details()` 产出的压缩表结构
  - 只把压缩后的 schema 传给 `generate_ontology_design_document()`
- 这样处理后：
  - 规则识别仍基于全部选表
  - 高层设计文档生成只基于压缩后的表结构摘要
  - 避免在设计文档阶段把全量列明细一次性送入模型
- 增加日志：
  - `Guide selected table schema compacted for design document`
  用于对比全量列数和压缩后列数，便于后续定位 prompt 膨胀来源。
- 同时把 `llm_selected_table_schema` 一并写入 blueprint payload，方便后续排查落库内容。

### 验证结果
- 执行：
  - `./.venv311/bin/python -m py_compile app/services/ontology_guide_service.py`
  - `npm run build`
- 结果：
  - 后端语法检查通过
  - 前端构建通过

### 结论
- 当前这类 53 万 tokens 级别的超限，根因是“高层设计文档生成阶段仍使用全量 schema”，不是简单业务文档过长。
- 修复后，Guide 可以继续保留“全量选表参与规则识别”，同时把高层设计文档阶段的 LLM 输入压缩到可控范围。

## 7. Guide 生成的关系名称优先统一为中文
### 背景
- 用户要求 Guide 自动生成业务实体与关系时，最终生成的对象关系名称尽量使用中文，而不是 `hasObservedMetric`、`occursOnUnit` 这类英文式关系名。
- 排查发现，现有流程里虽然提示词示例写了“关系名称，可中文”，但并没有强约束，也没有在最终蓝图构造阶段做中文化兜底。

### 改动文件列表
- `backend/app/services/llm_service.py`
- `backend/app/services/ontology_guide_service.py`

### 具体改动
- 强化 LLM 提示词约束：
  - `generate_relation_candidates()` 的输出格式说明改为：
    - `relationName: 关系名称，必须使用中文`
  - 同时在用户提示词中增加明确限制：
    - 必须使用中文
    - 不要输出 `hasXxx`、`belongsTo`、`occursOn`、`snake_case`、`camelCase` 这类英文关系名
    - 优先使用“触发异常”“关联批次”“命中规则”“发生于站位”这类简洁中文短语
  - `generate_ontology_design_document()` 中 `included_relations` 也同步要求 `relationName` 必须使用中文，避免高层设计文档阶段先产出英文关系名。
- 增加最终蓝图层的中文关系名兜底：
  - 在 `_build_ontology_design()` 中新增 `entity_display_map`
  - 新增 `_prefer_chinese_relation_name()`，用于在最终写入 blueprint 前统一关系名称：
    - 若关系名本身已含中文，则保留
    - 若关系说明是较短中文，则优先使用关系说明
    - 若关系名是英文式命名，则根据关键词推断动词并结合实体中文显示名重写，例如：
      - `trigger` / `cause` -> `触发`
      - `match` -> `匹配`
      - `occur` -> `发生于`
      - `against` / `violate` -> `违反`
      - `belong` -> `属于`
      - `include` / `has` -> `包含`
      - `use` -> `使用`
      - `derive` / `generate` -> `生成`
    - 最终形如：
      - `缺陷事件触发超差异常`
      - `测试会话包含观测指标`
      - `超差异常违反规则定义`
- 这样即使某次 LLM 仍输出英文风格关系名，最终 Guide 预览和落库 blueprint 中的关系名也会优先转成中文展示名。

### 验证结果
- 执行：
  - `./.venv311/bin/python -m py_compile app/services/llm_service.py app/services/ontology_guide_service.py`
  - `npm run build`
- 结果：
  - 后端语法检查通过
  - 前端构建通过

### 结论
- Guide 自动生成业务实体与关系时，关系名称已从“允许中文”提升为“默认要求中文 + 最终蓝图兜底转中文”。
- 后续用户在 Guide 预览和落库结果中，看到英文式关系名的概率将显著降低；即使模型偶发输出英文名，也会在最终蓝图阶段被优先改写为中文关系名。

## 8. 关系中文名不再受固定动词词表约束，改为业务语义优先
### 背景
- 用户进一步指出，关系名称不应被限制在“参与 / 触发 / 约束 / 归属 / 发生于”这类固定词表内，而应直接反映节点之间的业务关系信息。
- 排查发现，上一轮虽然已经要求中文关系名，但最终蓝图兜底函数 `_prefer_chinese_relation_name()` 仍基于一组英文关键词映射到固定中文动词，存在把业务关系语义压扁为泛化模板的风险。

### 改动文件列表
- `backend/app/services/llm_service.py`
- `backend/app/services/ontology_guide_service.py`

### 具体改动
- 进一步强化 LLM 提示词：
  - `generate_relation_candidates()` 中新增明确要求：
    - `relationName` 必须使用中文
    - 必须直接表达源节点与目标节点之间的业务语义关系
    - 不要局限于固定动词表
  - 增加更贴近业务语义的示例：
    - `规格规则判定超差事件`
    - `测试会话产生观测指标`
    - `产品单体参与测试会话`
    - `机台执行AA工序`
  - `generate_ontology_design_document()` 中 `included_relations` 也同步要求关系名直接表达业务语义，而不是抽象泛词。
- 调整最终蓝图层兜底策略：
  - `_prefer_chinese_relation_name()` 不再通过固定英文关键词词表强行映射为：
    - `触发`
    - `匹配`
    - `发生于`
    - `违反`
    - `属于`
    - `包含`

- 现状中 Guide 只支持：
  - 选择数据库连接
  - 读取远程表目录
  - 从数据库表中勾选业务关系表

    - 类型
    - 识别到的表数量
