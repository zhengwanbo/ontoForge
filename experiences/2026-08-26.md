## 图数据查询：受约束场景生成与路径命中验证

### 背景

图数据查询此前由大模型直接生成自由 Graph SQL，即使 SQL 能通过 Oracle 语法校验，也可能把同一锚点的并列关系错误串接。例如轮胎图把 `PROCESSEVENT → PROCESSSTEP` 与 `PROCESSEVENT → EQUIPMENT` 错写成 `PROCESSSTEP → EQUIPMENT`，导致完整路径返回 0 行。

### 改动文件

- `backend/app/services/source_data_service.py`
- `backend/app/services/llm_service.py`
- `backend/app/api/source_data.py`
- `backend/app/services/ddl_service.py`
- `backend/tests/test_graph_query_contract.py`

### 实施内容

- 新增属性图查询契约：从实际 Oracle 属性图元数据整理顶点标签、节点属性、边元素、边标签、精确源/目标端点、边属性与节点/边实例数量。
- LLM 不再直接输出 SQL，改为输出六条结构化查询计划；计划必须指定每条 `source_label → edge_element → target_label`、共享变量和所需属性。
- 后端仅根据图契约编译 `GRAPH_TABLE` SQL，拒绝不存在的关系、端点不匹配关系、无实例数据的边、变量标签冲突和不存在属性。
- 对编译 SQL 执行 Oracle 语法预检和 `ROWNUM = 1` 路径命中预检；任一场景失败会将错误反馈给模型重试一次，仍失败则不保存。
- 已保存的新场景带 `query_plan` 标记，可直接复用；旧的自由 SQL 缓存首次读取时仍执行兼容性预检。
- 后续生成 Property Graph DDL 时，边标签改为唯一的边存储对象名，不再把所有关系统一为 `GRAPH_LABEL`；已部署旧图需重新生成并执行属性图 DDL 后才会获得唯一边标签。

### 验证结果

- `cd backend && python -m py_compile app/services/source_data_service.py app/services/llm_service.py app/services/ddl_service.py app/api/source_data.py`：通过。
- `cd backend && python -m unittest tests.test_graph_query_contract tests.test_ddl_preflight_validation`：3 项通过。
- 使用轮胎真实属性图 `DM_1BBA4E0C90FC_PG` 回归：正确编译为 `TIRE → PROCESSEVENT`、`PROCESSEVENT → PROCESSSTEP`、`PROCESSEVENT → EQUIPMENT` 三条共享事件的并列路径；Oracle 语法预检通过，路径命中预检为 `True`。

## 关系边命名：英文谓词与重复实体名治理

### 背景

未命中固定中文关系词典时，旧逻辑会把源实体和目标实体一并写入谓词，再由边表名模板追加两端实体，产生 `..._EQUIPMENT_WORKSHOP_WORKSHOP` 一类重复名称。

### 改动文件

- `backend/app/services/llm_service.py`
- `backend/app/services/ontology_guide_service.py`

### 实施内容

- LLM 关系候选新增 `relationPredicate`：只允许输出大写英文动作谓词，如 `BELONGS_TO`、`USES`、`OCCURS_AT`，禁止带源/目标实体名或 `ONTO_EDGE_` 前缀。
- 生成边表名称时优先采用人工给出的 `relationTableName`，其次采用既有固定中文词典，再采用模型生成的 `relationPredicate`，最后统一回退为 `RELATED_TO`。
- 所有关系类型均使用 `ONTO_EDGE_<源实体>_<英文谓词>_<目标实体>` 的边对象命名，避免关系表分支绕过边标签命名规范。

### 后续操作建议

- 本体对象与已有映射不需要重新生成；仅对需要改名的关系确认/保存新的边对象名后，重新生成并执行受影响的 DDL（含属性图 DDL）。

## 多来源节点：属性投影完整性与关联规则

### 背景

节点属性在数据映射中可以分别命中多张业务表，但旧的实体级 `view_sql` 没有强制覆盖这些属性。多来源节点沿用早期 SQL 时，DDL 会只创建 SQL 最终 SELECT 中的少量列，形成“映射属性多、节点 DDL 属性少”的静默偏差。

### 改动文件

- `backend/app/services/llm_service.py`
- `backend/app/api/mapping.py`
- `backend/app/services/ddl_service.py`
- `backend/tests/test_multi_source_node_mapping.py`

### 实施内容

- 全域映射的 LLM 提示明确多来源节点必须定义锚点表/键、补充表 Join 键、基数和一对多收敛策略；补充表先按锚点键收敛一行，禁止直接裸 Join 多个明细表。
- 要求最终 SELECT 使用本体属性名别名输出全部已确认属性，并新增 `multiSourceJoinPlan` 结构供映射结果审阅。
- 后端解析 LLM 节点 SQL 的最终顶层 SELECT；若缺少任何确认属性，拒绝保存该节点设计并在映射结果中返回属性清单。
- DDL 预检对既有多来源实体级 SQL 执行同样核对并阻止生成，提示跳转数据映射修复；避免再部署不完整节点。

### 回归结果

- 当前 `Tire` 的历史节点 SQL 被正确识别缺少 13 个输出属性：`INSPECTION_ID`、最新检验字段及最后过程事件字段等。

## 数据映射管理：补齐多表实体语义整合视图入口

## 语义整合视图：保存后避免按物理源表读取
