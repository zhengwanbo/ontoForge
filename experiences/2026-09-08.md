## 本体对象语义与治理增强设计文档

### 背景

当前项目的本体建模页面和后端实体/属性/关系模型已经可用，但缺少面向业务语义和治理的结构化元数据。新需求要求补齐三类能力：

- 实体级对象类型：`fact / dim`
- 属性级业务语义：`unit / constraint / usage / isPrimaryKey / required filter / ref`
- 实体级治理信息：`status / data owner / security level / update frequency / tags`

由于仓库当前已经存在完整的本体 CRUD、Guide 自动生成与映射链路，设计必须基于现状落地，而不是另起一套并行模型。

### 参考现状

本次设计前重点阅读并核对了以下代码：

- `backend/app/models/models.py`
- `backend/app/schemas/schemas.py`
- `backend/app/api/ontology.py`
- `backend/app/api/mapping.py`
- `backend/app/services/ontology_guide_service.py`
- `frontend/src/views/ontology/OntologyBuild.vue`
- `frontend/src/api/index.ts`
- `experiences/2026-09-07.md`

确认到的关键现状：

- 实体当前只有 `build_type` 和技术 `status`，没有业务对象类型。
- 属性当前只有 `is_primary_key / is_nullable / data_type / desc` 等基础字段。
- 项目没有 Alembic，数据库结构演进依赖 `backend/app/main.py` 中的 `ensure_*_columns()` 方式补列。
- 映射侧已有 Join 分析能力，`ref` 最适合接入该链路，而不是只做展示字段。

### 产出文件

- `本体对象语义与治理增强设计方案.md`

### 设计结论

本次方案采用以下路线：

- 在 `sys_ontology_entity` 上直接扩展 `object_type` 和治理字段，不新建治理主表。
- 在 `sys_ontology_property` 上直接扩展 `unit / value_constraint / usage_codes_json / is_required_filter / ref_property_id`。
- 继续复用当前 `ontology.py` 的实体/属性 CRUD 接口，不新增一套平行 API。
- 前端在 `OntologyBuild.vue` 中增强实体弹窗、属性弹窗和右侧属性摘要。
- `OntologyGuideService` 需要扩展预览与应用逻辑，保证 AI 生成和人工维护使用同一套字段。
- `mapping.py` 需要让 `ref` 参与 Join 候选排序。

### 验证结果

- 已基于现有代码结构完成设计文档，字段命名、落库位置、接口修改点、前端入口、Guide 联动点和迁移方案都已与当前实现对齐。
- 本次未修改运行时代码，因此未执行 `npm run build` 或后端接口验证。

### 遗留问题

- `object_type` 历史数据如何回填，建议首版允许空值并通过前端逐步补齐。
- `ref_property_id` 是否做数据库级外键，本期建议先做应用层校验，避免 Oracle 历史环境改造风险。
- `usage` 是否单值或多值，设计中已建议采用多值 JSON，后续实现时仍需最终确认 UI 交互细节。

### 下一步建议

按设计文档中的顺序分四步实施：

1. 后端模型、Schema、CRUD 与补列逻辑
2. 前端 `OntologyBuild.vue` 的实体/属性编辑界面
3. Guide 预览与应用链路
4. 映射 Join 推荐对 `ref` 的消费

## 本体对象语义与治理增强功能实现

### 背景

在完成设计文档后，继续按方案直接实现本体对象语义与治理增强能力，目标是打通从数据库结构、后端 CRUD、Guide 应用、Join 推荐到前端页面维护的完整链路，而不是只补单点字段。

### 改动文件

- `backend/app/models/models.py`
- `backend/app/schemas/schemas.py`
- `backend/app/main.py`
- `backend/app/api/ontology.py`
- `backend/app/api/mapping.py`
- `backend/app/services/llm_service.py`
- `backend/app/services/ontology_guide_service.py`
- `frontend/src/views/ontology/OntologyBuild.vue`

### 实施内容

- 扩展本体实体表 `sys_ontology_entity`：
  - 新增 `object_type`
  - 新增治理字段 `governance_status / data_owner / security_level / update_frequency / governance_tags_json`
- 扩展本体属性表 `sys_ontology_property`：
  - 新增 `unit / value_constraint / usage_codes_json / is_required_filter / ref_property_id`
- 在 `backend/app/main.py` 中新增启动期补列逻辑：
  - `ensure_ontology_entity_semantic_columns()`
  - `ensure_ontology_property_semantic_columns()`
- 在 `backend/app/schemas/schemas.py` 中扩展实体和属性的创建、更新、响应结构，前后端都可传递并回显新增字段。
- 在 `backend/app/api/ontology.py` 中补齐统一语义字段处理：
  - 增加对象类型、治理状态、用途、标志位的校验与归一化
  - 增加 JSON 数组字段编解码
  - 增加 `ref_property_id` 同分析域校验和 `ref_display` 回显
  - 扩展实体列表、属性列表、实体创建更新、属性创建更新、图节点返回数据
  - 删除属性时会清理其他属性对它的 `ref_property_id` 引用，避免悬挂引用
- 在 `backend/app/services/ontology_guide_service.py` 中扩展 Guide 应用逻辑：
  - 支持落库 `objectType`、治理信息和属性语义信息
  - 增加二次解析，把 Guide 预览中的 `ref` 字符串或对象解析为真实 `property_id`
  - 兼容旧 blueprint，在覆盖应用时避免把缺失的新字段误清空
- 在 `backend/app/services/llm_service.py` 中扩展 blueprint 归一化：
  - 允许模型输出 `objectType / governanceInfo / unit / valueConstraint / usage / isRequiredFilter / ref`
  - 当模型未显式给出对象类型时，按对象名称和描述做轻量推断
- 在 `backend/app/api/mapping.py` 中增强关系 Join 候选分析：
  - 如果源属性明确 `ref` 目标属性，或目标属性反向 `ref` 源属性，则将该列对作为高优先级候选
- 在 `frontend/src/views/ontology/OntologyBuild.vue` 中增强本体建模页：
  - 实体编辑弹窗新增对象类型与治理信息
  - 属性编辑弹窗新增单位、约束、用途、必带过滤、引用属性
  - 图节点摘要新增对象类型展示
  - 右侧属性面板增加业务语义标签与 `ref` 摘要
  - 页面加载时额外读取实体目录，用于引用属性候选下拉

### 验证结果

- `python -m compileall backend/app`：通过，后端改动无语法错误。
- `cd frontend && npm run build`：通过，`vue-tsc` 和 Vite 构建成功。
- 前端构建仅出现既有的大 chunk 警告，不影响本次功能正确性。

### 遗留问题

- 本次未执行真实后端启动联调；当前仓库依赖 Oracle 连接，运行时验证仍需在可用数据库环境中完成。
- 自然语言调整服务 `ontology_adjustment_service.py` 本次未扩展对新增字段的生成/更新指令支持，当前新增语义字段主要通过人工编辑与 Guide 应用维护。
- Guide 预览界面本身还未单独增加对象类型、治理信息和属性语义的表格化展示，目前这些字段已可应用落库并在本体编辑界面回显。

### 下一步建议

1. 在可用 Oracle 环境中验证启动期补列、实体属性新增/编辑、`ref` 校验与回显。
2. 在映射页面实际选择一条带 `ref` 的关系，验证 Join 推荐是否按预期前置。
3. 若后续继续强化 AI 调整能力，再补 `ontology_adjustment_service.py` 和相应 LLM prompt 的新字段支持。
