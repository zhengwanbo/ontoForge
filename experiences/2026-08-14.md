## 本体关系构建图支持纵向滚动

### 背景
- “业务对象构建 > 本体关系构建”中的实体关系图在实体较多时，底部节点会超出可见区域，无法继续查看或操作。

### 改动文件列表
- `frontend/src/views/ontology/OntologyBuild.vue`
- `experiences/2026-08-14.md`

### 具体改动
- 图画布高度根据最底部实体节点的位置动态扩展，同时保留最小高度。
- 图区域改为独立的可滚动视口，超出视口时显示纵向滚动条；横向内容超出时也可正常查看。
- 拖拽坐标换算改用动态画布高度，避免滚动或扩展后的节点拖动出现偏移。

### 验证结果
- `cd frontend && npm run build` 通过（`vue-tsc` 类型检查和 Vite 构建成功）。
- `git diff --check` 通过。

### 遗留问题与下一步建议
- 可在实体数量较多的实际业务分析域中确认滚动条出现阈值和节点间距是否符合使用体验。

## 业务类型语义管理与 Guide 动态语义模式

### 背景
- 原 Guide 将生产缺陷/SFR 场景的四个语义模式固定在前后端；营销、供应链等通用领域会看到不适用的模式。
- 业务类型是业务分析域的上层语义约束，需由用户维护其业务语义描述和可选建模模式。

### 改动文件列表

- `backend/app/schemas/schemas.py`
- `backend/app/services/business_type_service.py`
- `backend/app/services/ontology_guide_service.py`

- `backend/app/api/domains.py`
- `backend/app/main.py`
- `frontend/src/api/index.ts`
- `frontend/src/router/index.ts`
- `frontend/src/views/Layout.vue`
- `frontend/src/views/business/BusinessTypeSemanticManage.vue`
- `frontend/src/views/business/BusinessDomainManage.vue`
- `frontend/src/views/ontology/OntologyBuild.vue`

### 具体改动
- 新增 `sys_business_type`，保存业务类型编码、名称、业务语义描述、启停状态及用户定义的语义模式（模式名称、说明、所需表角色、派生对象）。
- 初始化“业务主体域、制造对象域、分析场景域、自定义域”四类默认配置；允许创建、编辑、停用和删除未被业务分析域引用的自定义类型。

- Guide 根据当前业务分析域的类型动态加载模式及类型语义说明；自动推荐逻辑按用户定义的所需表角色执行。
- 后端 Guide 同步载入该类型的模式配置并传入 LLM 上下文，用户定义的模式会影响实体、关系和派生视图设计，不再被固定 SFR 模式覆盖。

## 语义模式去除表角色与派生对象约束

### 背景
- 跨行业数据的表名和对象命名差异很大，表角色不应成为业务语义模式的维护项或自动启用条件。
- 预设派生对象没有明确来源 SQL 时容易生成无法落地的概念节点。

### 具体改动
- 业务语义模式简化为编码、名称和业务语义说明；前端和 API 不再展示、保存或返回所需表角色及派生对象。
- Guide 不再按表角色自动勾选模式，改为由用户依据当前业务目标手工选择。
- 新增默认“供应链业务语义”和“营销业务语义”：前者预置主数据与层级、业务事件与单据、生命周期与状态、交易与流转；后者预置主数据与层级、业务事件与单据、生命周期与状态、指标与规则、案例与处置。
- 既有存储中的旧角色和派生对象字段在接口返回时被过滤，保证页面和 LLM 上下文不再使用它们。

### 验证结果
- `cd backend && python -m py_compile app/models/models.py app/schemas/schemas.py app/services/business_type_service.py app/api/business_types.py app/services/ontology_guide_service.py app/main.py` 通过。
- `cd frontend && npm run build` 通过；仅保留既有大体积 chunk 警告。

## 业务语义类型删除规则

### 背景
- 用户需要删除未被任何业务分析域引用的业务类型，包含预置类型。
- 若每次服务启动都补齐默认数据，删除后的类型会在重启后错误恢复。

### 具体改动
- 删除操作仅校验是否存在业务分析域引用，不再区分预置类型和用户新建类型。
- 新增一次性业务类型初始化标记表；首次启动补齐默认类型，之后不再自动补回被用户删除的类型。

### 验证结果

- `cd frontend && npm run build` 通过。

## LLM 自由生成改为选择业务语义模式

### 背景
- LLM 自由生成原先固定显示“通用规则”，无法明确本次本体生成采用哪些业务语义模式。

### 具体改动
- 在 LLM 自由生成策略下，顶部第二个选择器改为多选“本次业务语义模式”，选项来自当前业务分析域绑定的业务类型。
- 选择状态与 Guide 下方的手工模式勾选、已选标签保持同步，并在预览中显示当前业务类型及本次模式。
- 后端将 LLM 自由生成的场景标记由 `GENERAL_RULES` 改为 `BUSINESS_SEMANTIC`，避免将通用规则误解为固定业务目标；实际生成范围由业务类型描述和已选模式共同决定。

### 验证结果
- `cd backend && python -m py_compile app/services/ontology_guide_service.py` 通过。
- `cd frontend && npm run build` 通过。

## LLM 自由生成选择业务语义项目

### 背景
- 用户明确“业务语义模式”应指向业务语义管理中的项目（例如“营销业务语义”），而不是项目内部的模式明细。

### 具体改动
- LLM 自由生成顶部选择器改为选择业务语义项目，列出所有已启用的业务语义配置。
- 选择项目时自动载入其完整的语义描述和模式集合；这些模式作为该项目的整体提示词范围，不再要求用户逐项选择。
- 请求新增 `semantic_type_code`；后端仅在 LLM 自由生成中按此代码覆写当前次生成使用的业务语义配置，不修改业务分析域的持久化类型。
- 若所选项目不存在或已停用，后端返回明确错误。

### 验证结果
- `cd backend && python -m py_compile app/schemas/schemas.py app/api/ontology.py app/services/ontology_guide_service.py` 通过。
- `cd frontend && npm run build` 通过。

## DDL 边表主键错误定位增强

### 背景
- DDL 生成遇到关系两端节点缺少主键时，原错误仅显示关系名，无法确认是源实体还是目标实体需要修复。

- 错误信息直接指向“业务对象构建 > 本体关系构建”的属性 PK 标记修复入口。

### 验证结果
