## 设计结论

### 1. 菜单结构调整为分组式浏览
- 原来“本体浏览管理”是单个菜单项，只能进入一个页面。
- 本次改为分组菜单：
  - `本体浏览管理`
    - `本体图谱浏览`
    - `智能体构建`
      - `技能构建`
      - `智能体测试`
- 页面标题逻辑也同步调整，支持三级标题展示，例如：
  - `本体浏览管理 > 智能体构建 > 技能构建`

### 2. 后端新增独立 Agent Skill 模型
- 新增表 `sys_agent_skill`，避免把 skill 配置散落到流程表或本体表中。
- 表中保存：
  - 分析域
  - 流程
  - 本体对象
  - 技能名称/说明
  - 分析目标
  - 执行规则
  - 输出要求
  - 自动生成的 prompt 模板
  - 技能上下文快照 `context_json`
  - 状态与创建信息
- 由于项目当前使用 `Base.metadata.create_all()` 建表，没有迁移框架，因此新增模型即可随服务启动自动创建表。

### 3. 后端新增 Agent API 与测试服务
- 新增路由 `backend/app/api/agent.py`，统一挂到 `/api/v1/agent`。
- 提供接口：
  - `GET /agent/skills`
  - `GET /agent/skills/{skill_id}`
  - `POST /agent/domains/{domain_id}/skills`
  - `PUT /agent/skills/{skill_id}`
  - `DELETE /agent/skills/{skill_id}`
  - `POST /agent/skills/{skill_id}/test`
- 新增 `AgentService`，负责：
  - 读取分析域、流程、本体对象、属性、关系
  - 自动生成 skill prompt 模板
  - 生成 skill 上下文快照
  - 解析流程图 JSON，提取流程步骤顺序
  - 在测试时读取 graph 表结构与样例数据
  - 基于本体属性与表字段做匹配
  - 输出流程执行轨迹、建议 SQL、测试 Prompt、结果摘要与风险告警

### 4. 新增“技能构建”页面

## 补充改动内容

### 1. 新增一次性 Oracle 元数据迁移脚本
- 新建 `backend/scripts/migrate_oracle_metadata.py`。
- 脚本能力：
  - 连接远端/本地 Oracle
  - 备份本地目标表到 JSON
  - 按依赖顺序清空本地元数据表
  - 按依赖顺序从远端全量导入本地
  - 处理 Oracle `CLOB/BLOB/LOB locator`
  - 处理 JSON 字段被驱动读取为 `dict/list` 的情况
  - 以“源表列 ∩ 目标表列”的交集方式导入，兼容远端/本地 schema 细微差异

### 2. 先初始化本地 schema，再执行迁移
- 排查发现：
  - 远端 `oonbuild` schema 下已有全部 `SYS_*` 元数据表
  - 本地 `oonbuild@freepdb1` 初始为空 schema，没有任何项目表
- 因此先执行了基于 SQLAlchemy 模型的 `Base.metadata.create_all(...)`，在本地建出项目元数据表，再执行数据迁移。

### 3. 迁移后将项目默认数据库切换到本地
- `backend/.env` 中的 `DATABASE_URL` 已从远端 `orclpdb1` 改为本地 `freepdb1`：
  - 变更前：`163.192.218.148:1521/?service_name=orclpdb1`
  - 变更后：`localhost:1521/?service_name=freepdb1`
- 这样后续本地启动后端时，会直接读取本地 Oracle 中的元数据，不再继续连远端元数据库。

## 处理过程中遇到的问题
- 第一次迁移结果全为 0，原因不是连接失败，而是本地 schema 为空，没有表。
- 第二次迁移时，Oracle 驱动把部分 JSON/CLOB 字段读成了 Python `dict/list`，直接绑定失败，已转成字符串后解决。
- `SYS_DDL_LOG` 导入时触发 `ORA-65011`，根因是跨库搬运 Oracle LOB locator；已改为先读出 LOB 内容再导入，问题解决。
- 本地备份阶段也遇到 Oracle 对象无法直接 JSON 序列化的问题，已统一在读取行数据时做归一化。

## 补充改动内容

### 1. 在数据源服务层提前消化 Oracle LOB
- `SourceDataService._normalize_cell_value(...)` 新增对 `LOB` 的处理：
  - 若对象带 `read()` 方法，立即读取内容
  - 递归转成普通字符串/基础类型
  - 若读取失败，返回 `None`
- 这样保证离开数据源服务层之前，返回给上层的内容不再携带悬空 LOB 句柄。

### 2. 补齐表注释 / 列注释 / 表列表注释的归一化

  也统一转成普通可序列化值
- 这样自动映射用到的候选表元数据不会再混入 Oracle 原生对象。

### 3. LLM 层不再对异常 LOB 兜底调用 `str(value)`
- `LLMService._make_json_safe(...)` 中：
  - 以前 `read()` 失败会走 `str(value)`
  - 但 Oracle `LOB.__str__()` 本身又会触发 `read()`
  - 这就形成二次异常
- 现在改为：
  - 若 `read()` 失败，直接返回 `None`
- 避免在提示词构造阶段再次触发数据库访问。
