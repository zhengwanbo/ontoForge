## 实体级 view_sql 与已确认属性映射的优先级修正

### 背景

金鼎仙泉营销分析域的 `PromotionRule` 已为 `SKU_SCOPE`、`CONDITION_DESC`、`REWARD_DESC` 保存了 `DIRECT + CONFIRMED` 的来源列映射，但全域映射早期生成的实体级 `view_sql` 仍包含 `CAST(NULL AS CLOB)`。DDL 生成器此前无条件优先使用该实体级 SQL，导致已确认的属性映射被旧占位表达式覆盖。

### 改动

- 修改 `backend/app/services/ddl_service.py`。
- 对普通单源、无 Join/过滤/分组等复杂逻辑的实体级 SQL，不再直接复用 LLM 生成的投影，而是根据当前属性映射重新构建来源查询。
- 对需要保留的多表或复杂实体级 SQL，使用已维护的 `DIRECT` / `COMPUTED` 属性映射回填 `CAST(NULL AS <type>) AS <property>` 占位列。
- 保留未映射属性的空值兜底，并继续修正不带长度的 `CAST(NULL AS VARCHAR2)`。

### 验证

- `python -m py_compile backend/app/services/ddl_service.py`：通过。
- `git diff --check`：通过。
- 只读加载当前 `PromotionRule` 配置并调用 DDL 来源 SQL 生成：`SKU_SCOPE`、`CONDITION_DESC`、`REWARD_DESC` 均输出为 `src.<column> AS <property>`，结果中不存在 `CAST(NULL AS CLOB)`。

### 后续建议

- 全域映射生成阶段可继续降低普通单表节点写入实体级 `view_sql` 的频率；复杂 Join、过滤和计算场景才保存该 SQL。

### 背景

### 改动

- 在 `backend/app/api/source_data.py` 新增 `GET /source/graph-query/recommendations`。
- 接口验证当前业务分析域与 Oracle 数据源的归属关系，再通过 Oracle 属性图数据字典读取实际图名称，生成六条只读 `GRAPH_TABLE` 查询：直接关联、两跳流转、关联邻域、下游、上游和顶点实例概览。
