## Guide 高层本体设计文档空内容修复

### 背景

分步骤生成的“本体逻辑设计”使用 LLM 模型辅助并上传营销需求文档后，高层本体设计文档页面的业务范围、目标、边界、对象关系等字段为空。

### 改动文件

- `backend/app/services/llm_service.py`
- `backend/app/services/ontology_guide_service.py`
- `backend/tests/test_ontology_guide_prompt_compaction.py`
- `frontend/src/views/ontology/OntologyBuild.vue`

### 实施内容

- 修复高层设计提示词只传递通用业务摘要、未传递上传文档正文的问题；现在将 Markdown 格式的需求文档正文（最多 16,000 字符）直接提供给大模型，以便识别营销对象清单、关系、边界和业务术语。
- 修复将 `{ "mappings": [] }` 等无关 JSON 误判为有效本体设计文档的问题；此类响应会触发明确的 `fallback` 结果，不再保存为空白设计。
- 降级设计文档保留文档提纲、业务范围、待确认项和后续数据表类型，并在前端显示醒目的模型返回异常提示，禁止将空白结果误认为可确认设计。
- 对仅返回旧版范围字段的模型结果，补全业务范围、核心对象和逻辑关系的展示兜底内容。
- 新增回归测试，覆盖无关 mock 响应识别和可审阅的降级设计文档。
- 诊断当前运行配置：默认 LLM 为 `gpt-5.4`，网关 `http://163.192.218.148:4000` 在 TCP 连接阶段超时；DeepSeek 备用端点也在当前运行环境连接超时。因此页面返回的是连接异常后的 mock/fallback，而非营销文档解析问题。保底设计文档现会携带并在前端展示底层 `generation_error`，便于直接定位网关、鉴权或返回格式故障。

## 数据补全与逻辑本体的数据支撑区分

### 背景

数据补全阶段的 LLM 仅识别出部分有数据来源的对象，但服务在与逻辑蓝图合并之前就持久化了该子集。前端刷新“最新蓝图”后读取了子集，导致逻辑设计中的 44 个对象看似变成 28 个；全域自动映射也会扫描没有数据依据的逻辑对象。

### 改动文件

- `backend/app/services/ontology_guide_service.py`
- `backend/app/api/mapping.py`
- `backend/tests/test_ontology_guide_prompt_compaction.py`
- `frontend/src/views/ontology/OntologyBuild.vue`
- `frontend/src/views/mapping/DataMappingOperation.vue`

### 实施内容

- 数据补全改为先与已确认逻辑蓝图合并，再保存完整结果，避免最新蓝图覆盖逻辑对象全貌。
- 对实体、属性、关系标记 `DATA_SUPPORTED`、`DATA_CANDIDATE`、`LOGICAL_ONLY`：实体和属性要求实际来源表/字段，边还要求两端实体、证据表和 Join/edge SQL；缺 Join 的边标为待确认候选。
- 数据补全预览新增数据支撑统计和标签，明确哪些实体/边可自动映射、哪些仅逻辑保留。
- 全域自动数据映射仅扫描数据补全蓝图中 `DATA_SUPPORTED` 的实体和边；逻辑保留对象以 `SKIPPED_NO_DATA_SUPPORT` 显示，不会再发给 LLM 自动映射。
- 数据映射操作页显示可自动映射实体、逻辑保留实体和跳过数量。

### 验证结果

- `cd backend && python -m py_compile app/api/mapping.py app/services/ontology_guide_service.py app/services/llm_service.py`：通过。
- `cd backend && python -m unittest tests.test_ontology_guide_prompt_compaction`：9 项通过。
- `cd frontend && npm run build`：通过；仅保留既有构建产物体积提示。
- `git diff --check`：通过。

## 数据映射仅处理有数据支撑对象与关系候选修复

### 背景

数据映射操作仍可能读取泛化的最新蓝图，导致逻辑本体也进入映射任务；同时原有关系筛选只允许已经具备 Join 的 `DATA_SUPPORTED` 关系进入任务。两端节点和关系证据表均存在、但 Join 尚待识别的 `DATA_CANDIDATE` 关系被提前排除，表现为关系映射反复为 0。

### 改动文件

- `backend/app/api/mapping.py`
- `frontend/src/views/mapping/DataMappingOperation.vue`

### 实施内容

- 新增并统一使用“最近一次数据补全蓝图”读取逻辑；全域映射没有数据补全结果时明确拒绝执行并提示先完成数据补全设计，不再悄然映射所有逻辑实体。
- 仅 `DATA_SUPPORTED` 实体进入属性和节点映射；逻辑保留实体只以“未映射”说明展示，不调用模型、不创建映射。
- `DATA_CANDIDATE` 关系也进入关系映射：其两端实体和关系证据表已经存在，数据映射阶段负责识别和验证 Join；`LOGICAL_ONLY` 关系仍不进入任务。
- 全局关系设计前补充加载独立关系证据表的表结构，确保诸如单独关系表描述的编码关联不会因未被节点属性映射选中而缺失。
- 任务摘要区分可映射对象数、逻辑对象数及跳过数量；映射操作页也改为展示数据补全设计包和实际执行范围。

## 关系映射全为零的运行时异常修复

### 背景

最近一次营销域全域映射任务已纳入 27 条数据支撑关系候选，但全部为 `EMPTY`。读取任务记录确认，根因不是关系候选筛选，而是整体属性图设计调用模型前抛出 `Object of type timedelta is not JSON serializable`；异常处理回退为空的节点、关系设计，因此没有产生任何 Join 建议。

### 改动文件

- `backend/app/services/llm_service.py`
- `backend/tests/test_ontology_graph_mapping_design.py`

### 实施内容

- LLM 提示词安全序列化新增 `timedelta` 支持，将 Oracle `INTERVAL` 样例值规范为可读字符串。
- 这样带 Oracle 间隔类型字段的源表可进入整体节点/关系设计，已验证的同名 FK→PK Join 可以由确定性规则补入；其他候选关系再由模型依据关系证据表识别 Join。
- 增加 Oracle `INTERVAL` 样例进入关系设计提示词的回归测试。

## 一体化生成纳入自动数据映射范围

### 背景

### 改动文件

- `backend/app/services/ontology_guide_service.py`
- `backend/app/api/mapping.py`
- `frontend/src/views/mapping/DataMappingOperation.vue`
- `backend/tests/test_ontology_guide_prompt_compaction.py`
