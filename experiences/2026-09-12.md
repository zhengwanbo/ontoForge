并要求以 `database/oracle/jylt/ontology_view_pgq.sql` 为样例，把对应业务分析域“金鱼轮胎生产质量追溯”中的本体对象、属性、关系及映射信息补充到平台库。

### 实施内容

本次新增了通用反向导入工具 `import_oracle_pgq_ddl_metadata.py`。

工具能力：

- 解析 `CREATE OR REPLACE VIEW ONTO_NODE_*`
- 解析 `CREATE OR REPLACE VIEW ONTO_EDGE_*`
- 解析 `CREATE OR REPLACE PROPERTY GRAPH`
- 解析 `COMMENT ON TABLE`
- 反推出：
  - `SYS_ONTOLOGY_ENTITY`
  - `SYS_ONTOLOGY_PROPERTY`
  - `SYS_ONTOLOGY_RELATION`
  - `SYS_ENTITY_MAPPING`
  - `SYS_PROPERTY_MAPPING`
  - `SYS_RELATION_MAPPING`

导入策略：

- 默认 `dry-run`，仅输出摘要
- 传入 `--apply` 后写入当前平台数据库
- 采用“按域增量 upsert”方式：
  - 实体按 `table_name / entity_name` 匹配更新
  - 关系按 `relation_table_name / relation_name + 两端实体` 匹配更新
  - 属性按 `property_name` 更新
- 不依赖重新生成 Guide、Blueprint 或 DDL 日志，专注恢复本体与映射元数据

本次对 `jylt` 样例的解析规则：

- `ONTO_NODE_*` 视图对应平台实体
- `PROPERTY GRAPH` 中的 `KEY + PROPERTIES` 对应平台属性
- `COMMENT ON TABLE ONTO_NODE_*` 的中文前缀回填为 `entity_display_name`
- `ONTO_EDGE_*` 视图对应平台关系
- `edge_sql` 直接保存为关系映射证据
- `relation_cardinality` 采用受控启发式推断
- `entity_mapping.view_sql` 保存节点视图完整 SQL
- `property_mapping` 默认回填到节点视图输出列级别，确保平台中能完整展示映射信息

### 遗留问题

- 当前属性映射恢复到“节点视图输出列”层级，而不是继续追溯到更底层源表字段级血缘
- 当前 `relation_cardinality` 为启发式推断，后续若需要更精确基数，可继续增强解析器
- 当前工具主要适配 `ONTO_NODE_* / ONTO_EDGE_* / PROPERTY GRAPH` 风格 DDL；若 DDL 风格差异很大，可能需要补更多解析规则

### 下一步建议

1. 若需要更细粒度的数据血缘，可继续扩展脚本，对 `SELECT ... AS ...` 的表达式和中间 `VW_* / MV_*` 视图做递归解析。
2. 若后续希望页面直接触发导入，可在系统管理或 DDL 管理中补一个受控后台接口，包装该脚本能力。
3. 对其他业务域复用时，建议先用 dry-run 输出摘要确认实体/关系数，再执行 `--apply`。

## 本体、映射与 DDL 多版本支撑设计文档

### 背景

用户提出当前系统在每个业务分析域下，本体对象、数据映射、DDL 生成与 graph 落地都只有一份“当前版本”，无法同时支撑：

- 同一业务域多个本体实现版本
- 不同版本下各自独立的数据映射
- 基于某一版本映射结果生成该版本专属 DDL
- 多个不同版本 graph 对象并存验证

因此需要基于本项目现有架构，设计一套较完整的多版本支撑方案，并输出正式 Markdown 设计文档。

### 参考现状

本次设计前重点复核了以下位置：

- `backend/app/models/models.py`
- `backend/app/api/mapping.py`
- `backend/app/api/ddl.py`
- `backend/app/services/ontology_guide_service.py`
- `docs/guide-ontology-generation-flow.md`
- `RELEASE_NOTES.md`

确认到的关键现状：

- 当前仅 `SYS_ONTOLOGY_BLUEPRINT.version_no` 具备版本概念
- 但真正落库的：
  - `SYS_ONTOLOGY_ENTITY`
  - `SYS_ONTOLOGY_PROPERTY`
  - `SYS_ONTOLOGY_RELATION`
  - `SYS_ENTITY_MAPPING`
  - `SYS_PROPERTY_MAPPING`
  - `SYS_RELATION_MAPPING`
  - `SYS_DDL_LOG`
  仍然只有“每域一份当前态”
- 当前 DDL 生成与执行仍主要依赖“当前域当前实体/映射”
- 当前 Oracle graph 对象也默认只有一套技术名称，不支持同域多版本并存

### 改动文件

- `docs/本体映射DDL多版本支撑设计方案.md`
- `experiences/2026-09-12.md`

### 实施内容

本次新增正式设计文档 `docs/本体映射DDL多版本支撑设计方案.md`，核心设计包括：

- 区分：
  - `Blueprint` 设计版本
  - `Ontology Version` 运行实现版本
- 新增版本主表：
  - `SYS_ONTOLOGY_VERSION`
- 建议为本体、映射、DDL 等核心表补：
  - `version_id`
  - 以及实体/属性/关系级 `lineage_id`
- 设计版本生命周期：
  - `DRAFT`
  - `MAPPING`
  - `READY_FOR_DDL`
  - `DEPLOYED`
  - `ARCHIVED`
- 设计 Oracle 物理对象版本命名规则：
  - `ONTO_NODE_*_V001`
  - `ONTO_EDGE_*_V001`
  - `GRAPH_NAME_V001`
- 设计 DDL 执行日志与运行态部署记录拆分：
  - `SYS_DDL_LOG`
  - `SYS_GRAPH_DEPLOYMENT`
- 设计前端各模块版本化改造点：
  - 业务域版本管理
  - Guide “应用为新版本”
  - 本体关系构建版本切换
  - 数据映射管理版本切换
  - DDL 按版本生成与执行
  - 图浏览 / 图查询 / Agent Skill 绑定版本
- 设计数据迁移与兼容策略：
  - 为现有每个域生成初始化版本
  - 过渡期允许按默认编辑版本或默认运行版本回退

- 本次为架构设计文档输出，不涉及可执行代码，因此未运行构建或测试

- 多版本范围目前在文档中已扩展到规则、活动、流程、Skill，但实际实施建议仍应先聚焦“本体 + 映射 + DDL + 浏览”主链路
