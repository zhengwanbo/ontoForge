## Oracle 26ai DDS Python 脚本：切换到当前环境可用的 TCPS 连接

### 背景

根目录临时脚本 `test_end_user.py` 原先使用 `localhost:1521/freepdb1` 的普通 `tcp` 连接，并直接把业务 claims 字典传给 `set_end_user_security_context()`，执行时触发 `DPY-2073: end_user_security_context requires use of the tcps protocol`。进一步核查发现，本机已经存在 `../oracleDeepDataSec/wallet` 与 `tcps://localhost:2484/freepdb1` 的可用钱包配置，但当前环境未配置真实 Entra 所需的 `DB_ACCESS_TOKEN` / `AZURE_*`，因此共享账号模式下只能先验证 TCPS 连通性，不能默认注入终端用户安全上下文。

### 改动文件

- `test_end_user.py`

### 实施内容

- 将脚本改为自动加载多个环境文件：优先补齐 `backend/.env`、仓库根 `.env` 与 `../oracleDeepDataSec/.env`。
- 支持从已加载 `.env` 所在目录解析相对路径形式的 `DB_CONFIG_DIR` 与 `DB_WALLET_LOCATION`，直接复用 `oracleDeepDataSec` 里的 wallet。
- 默认走 `dds_app` 共享数据库账号，通过 `tcps://localhost:2484/freepdb1` 建立 Oracle 26ai Thin 连接并打印：
  - `SESSION_USER`
  - `NETWORK_PROTOCOL`
  - `AUTHENTICATED_IDENTITY`
  - `ENTERPRISE_IDENTITY`
  - `ORA_END_USER_CONTEXT`
- 若显式提供 `DB_ACCESS_TOKEN`，脚本再尝试调用 `oracledb.create_end_user_security_context()` 与 `connection.set_end_user_security_context()`。
- 终端用户身份支持两种输入：
  - `END_USER_TOKEN`
  - `END_USER_IDENTITY + END_USER_KEY`
- 保留可选的本地 `END USER` 直连探测；只有设置 `LOCAL_END_USER_USERNAME` 时才尝试，避免当前环境默认因演示口令不一致而直接失败。
- 修复 `ORA_END_USER_CONTEXT` 在当前 `python-oracledb 4.0.0` 环境下返回 `str` 而非 LOB 对象时的兼容处理。

### 验证结果

- `python test_end_user.py`：通过，当前输出确认：
  - 已加载 `/Users/wanzheng/src/ontoForge/backend/.env`
  - 已加载 `/Users/wanzheng/src/oracleDeepDataSec/.env`
  - `SESSION_USER = DDS_APP`
  - `NETWORK_PROTOCOL = tcps`
  - `ORA_END_USER_CONTEXT = {}`
  - 未提供 `DB_ACCESS_TOKEN` 时给出明确提示，并跳过本地 `END USER` 探测
- `python -m py_compile test_end_user.py`：通过。
- 使用测试环境变量实际触发 `set_end_user_security_context()`：
  - `DB_ACCESS_TOKEN='test-db-access-token' + END_USER_TOKEN='<测试 JWT 字符串>' + python test_end_user.py`
  - `DB_ACCESS_TOKEN='test-db-access-token' + END_USER_IDENTITY='maria.garcia@contoso.example' + END_USER_KEY='EndUserDemo#2026' + python test_end_user.py`
  - 两条路径都会先成功建立 `DDS_APP / tcps` 共享连接，并执行 `connection.set_end_user_security_context(...)`，随后在再次查询会话上下文时返回 `ORA-52602: Invalid database access token in the end-user security context: Failed to parse token`
  - 说明当前失败点已经从最初的 `DPY-2073 / 非 TCPS` 前置条件，推进为数据库侧对 `database access token` 的真实性校验。

### 遗留问题

- 当前库环境尚未提供真实 `DB_ACCESS_TOKEN`，因此无法在 Python 侧实际完成共享账号模式的 `set_end_user_security_context()` 注入验证。
- 以占位字符串或伪造 JWT 作为 `DB_ACCESS_TOKEN` 时，Oracle 26ai 会在真正执行 SQL 时返回 `ORA-52602`，拒绝继续使用该 end-user security context。
- `../oracleDeepDataSec/.env` 中的 `LOCAL_END_USER_PASSWORD=EndUserDemo#2026` 与当前数据库实际本地 `END USER` 口令不一致或本地 `END USER` 尚未初始化，直接登录验证此前返回 `ORA-01017`。
- 当前连接的 `dds_owner.hr_secured_records` 视图不存在，说明 sibling 仓库的 HR 演示对象没有完整部署到这台 `FREEPDB1`。

### 下一步建议

- 若要验证共享账号模式，先补齐真实 Entra 的 `DB_ACCESS_TOKEN` 与 `END_USER_TOKEN`，再运行 `python test_end_user.py`。
- 若要验证本地 `END USER` 模式，先确认数据库已执行 `oracleDeepDataSec` 的本地 DDS 初始化脚本，并设置 `LOCAL_END_USER_USERNAME` 后重跑。
