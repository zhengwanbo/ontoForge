## 智能体测试读取记录数上限放开

### 背景

用户反馈“智能体构建 > 智能体测试”中的“读取记录数”默认是 100，且无法继续调大。需要允许用户手工增减该值，而不是被固定在 100 条以内。

### 参考现状

本次修改前先阅读并确认了以下位置：

- `frontend/src/views/agent/AgentTest.vue`
- `backend/app/schemas/schemas.py`
- `backend/app/services/agent_service.py`
- `experiences/2026-09-08.md`

确认到的限制点有三处：

- 前端 `AgentTest.vue` 中 `el-input-number` 的 `max` 写死为 `100`
- 后端 `AgentSkillTestRequest.sample_limit` 校验上限写死为 `100`

这意味着只改前端输入框并不能真正放开读取记录数，必须同步改后端。

- 后端 `AgentSkillTestRequest.sample_limit` 的 Pydantic 校验上限从 `100` 调整为 `1000`

## DDL 生成与应用：将本体属性描述写入 table/view 列 comments

### 背景

用户要求在 DDL 生成与应用时，将本体对象属性定义中的描述同步写入最终落库对象的列注释中：

- 如果本体对象构建为 `TABLE`，则写入目标表列的 `COMMENT ON COLUMN`
- 如果本体对象构建为 `VIEW`，则写入目标视图列的 `COMMENT ON COLUMN`

现有 `DDLService._generate_comments_ddl()` 已经会生成列注释，但对“显式实体 SQL”只通过 `AS 别名` 识别输出列，遇到裸列别名或省略 `AS` 的视图 SQL 时，可能漏判投影列或错误保留不存在列的注释。

### 参考现状

本次修改前重点阅读并确认了以下代码：

- `backend/app/services/ddl_service.py`
- `backend/app/api/ddl.py`
- `backend/tests/test_ontology_graph_mapping_design.py`
- `experiences/2026-09-09.md`

确认到的关键现状：

- DDL 模板生成时，`_generate_template_ddl()` 已经会在对象 DDL 后追加 `_generate_comments_ddl()`
- `_generate_comments_ddl()` 中列注释来源本来就是 `prop.property_desc or prop.property_display_name or prop.property_name`
- 但显式 SQL 的投影列识别仅依赖正则提取 `AS alias`，不够稳健

### 改动文件

- `backend/app/services/ddl_service.py`
- `backend/tests/test_ontology_graph_mapping_design.py`

### 实施内容

- 保留现有“列注释来源优先使用本体属性描述 `property_desc`”的规则
- 强化 `DDLService._generate_comments_ddl()`：
  - 显式 SQL 的投影列不再只靠 `AS alias` 识别
  - 改为复用更稳健的最终 `SELECT` 投影解析能力，只给实际输出列生成 `COMMENT ON COLUMN`
- 新增 SQL 投影解析辅助方法：
  - `_split_top_level_sql_items()`
  - `_extract_projection_alias()`
  - 兼容如下写法：
    - `expr AS COL`
    - `expr COL`
    - `table.COL`
    - `COL`
- 新增 `_escape_oracle_comment()`，对注释内容中的单引号做 Oracle 转义，避免属性描述包含 `'` 时生成无效 DDL
- 因为 `COMMENT ON COLUMN <object>.<column>` 对表和视图都按最终对象名生成，所以 `TABLE` 和 `VIEW` 场景都会自动落到各自列 comments 上

## DDL 生成与应用：将本体属性业务元数据写入 Oracle 列 annotations

### 背景

在已经把本体属性描述落到 table/view 列 comments 后，继续根据用户要求，将属性级业务元数据也写入 Oracle 列 annotations，至少覆盖：

- 单位 `unit`
- 值域约束 `value_constraint`
- 用途 `usage`
- 必带过滤 `is_required_filter`
- 引用关系 `ref`

这样 DDL 执行落库后，列的结构化业务语义既能从 comments 看到说明，也能从 annotations 读取机器可消费元数据。

### 参考现状

本次修改前重点阅读并确认了以下位置：

- `backend/app/services/ddl_service.py`
- `backend/tests/test_ontology_graph_mapping_design.py`
- `experiences/2026-09-09.md`

确认到的关键现状：

- `DDLService._generate_template_ddl()` 已经会在节点 table/view DDL 后追加 comments 语句
- 但尚未生成 Oracle `ANNOTATIONS(...)` 语句
- 视图场景需要走 `ALTER VIEW ... MODIFY (...)`，不能简单套用表的 `ALTER TABLE ... MODIFY ...`

### 改动文件

- `backend/app/services/ddl_service.py`
- `backend/tests/test_ontology_graph_mapping_design.py`

### 实施内容

- 在 `DDLService._generate_template_ddl()` 中，紧接已有 comments 之后，新增属性列 annotations 生成流程
- 新增 `_generate_column_annotations_ddl(entity, entities)`：
  - 对当前实体的每个本体属性生成结构化 annotations DDL
  - `TABLE` 对象输出 `ALTER TABLE ... MODIFY col ANNOTATIONS(...)`
  - `VIEW` 对象输出 `ALTER VIEW ... MODIFY (col ANNOTATIONS(...))`
- 新增 `_build_property_annotation_items()`，将本体属性元数据映射为以下 annotation 名称：
  - `ONTOLOGY_UNIT`
  - `ONTOLOGY_VALUE_CONSTRAINT`
  - `ONTOLOGY_USAGE`
  - `ONTOLOGY_REQUIRED_FILTER`
  - `ONTOLOGY_REF`
- `usage` 以 JSON 数组字符串写入 annotation 值，保留多值语义
- `ref` 不写内部 `property_id`，而是写可读的 `实体名.属性名`，例如 `Store.store_id`
- 为了保证重复执行 DDL 时尽量幂等，每个 annotation 先生成 `DROP IF EXISTS`，再生成 `ADD`
- annotations 同样只对最终实际投影到 table/view 中的列生成，避免对不存在列执行注解 DDL
- 补充 DDL 语句类型识别，使执行结果展示和 DDL 合并过滤逻辑能够识别新的 annotation 语句

### 验证结果

- `python -m compileall backend/app/services/ddl_service.py backend/tests/test_ontology_graph_mapping_design.py`：通过
- 定向单测通过：
  - `test_generates_table_column_annotations_from_property_metadata`
  - `test_generates_view_column_annotations_only_for_projected_columns`
  - `test_filters_llm_property_graph_and_comments_only_projected_columns`
  - `test_comments_support_bare_projection_alias_and_escape_quotes`

### 遗留问题

- 本次仅生成并验证了 DDL 文本，尚未在真实 Oracle 目标库中执行后再回读 `USER_ANNOTATIONS_USAGE` 做集成验证
- 当前 annotation 命名采用平台内部前缀 `ONTOLOGY_*`，后续如需统一为企业级元数据规范，可再统一调整

### 下一步建议

1. 选择一个 table 节点和一个 view 节点分别生成 DDL，检查输出中的 `ALTER TABLE ... ANNOTATIONS(...)` 与 `ALTER VIEW ... ANNOTATIONS(...)`。
2. 执行 DDL 后查询 `USER_ANNOTATIONS_USAGE`，确认列 annotations 已落库并可回读。

## Agent Skill 构建增强：按分析场景驱动分析模式

### 背景

在上一轮 SkillBuilder 已支持手工选择分析模式、指标、规则和活动后，用户进一步提出：分析模式不应是通用配置，而应按业务场景变化。例如质量缺陷分析和供应链分析所需的分析模式组合、入口对象和业务语义范围并不相同，因此需要把“场景”提升为更高层的配置入口。

### 参考现状

本次修改前确认了以下现状：

- `SkillBuilder` 中的 `analysis_modes` 仍主要靠人工多选
- 后端 `analysis-semantics` 接口虽已返回指标、规则、活动，但尚未内置场景模板
- `context_json` 与 Skill 包中未显式保存“分析场景”这一层业务意图

### 改动文件

- `backend/app/schemas/schemas.py`
- `backend/app/services/agent_service.py`
- `frontend/src/views/agent/SkillBuilder.vue`
- `backend/tests/test_agent_skill_semantics.py`

### 实施内容

- Skill schema 增加 `analysis_scenario_code`
- 后端内置并返回多种场景模板：
  - `QUALITY_DEFECT`
  - `QUALITY_ROOT_CAUSE`
  - `SUPPLY_TRACE`
  - `SUPPLY_IMPACT`
  - `GENERAL_GRAPH`
- 每个场景模板都带出：
  - 推荐分析模式
  - 默认时间窗
  - 最大路径跳数
  - 是否默认启用活动建议
  - 推荐入口对象
  - 推荐指标 / 规则 / 活动集合
- 推荐集合不是写死 ID，而是根据当前分析域内实体、指标、规则、活动的名称和说明关键词动态匹配
- `AgentService._load_analysis_semantics_for_skill()` 支持在用户未手工覆盖时，直接套用场景模板默认值
- `analysis_profile` 现在会记录：
  - `analysis_scenario_code`
  - `analysis_scenario_name`
  - 场景对应的分析模式和执行边界
- `SKILL.md` 和 `analysis-strategy.md` 也会显式写出分析场景
- 前端 `SkillBuilder` 新增“分析场景”下拉框
  - 用户选择场景后，会自动带出推荐分析模式、入口对象、指标、规则、活动、时间窗和路径跳数
  - 分析模式仍可继续人工微调，但默认来源已经由场景驱动

### 验证结果

- `cd backend && python -m compileall app/schemas/schemas.py app/services/agent_service.py tests/test_agent_skill_semantics.py`：通过
- `cd backend && python -m unittest tests.test_agent_skill_semantics`：通过
- `cd frontend && npm run build`：通过
- 新增定向单测验证：
  - 供应链追溯场景模板能生成正确推荐模式
  - Skill 语义装载在未手工指定时会自动采用场景默认值

### 遗留问题

- 当前场景模板是基于关键词匹配推荐，适合作为第一版默认策略；如果后续分析域越来越多样，可能需要升级为可配置场景模板
- 当前前端场景切换会直接覆盖当前语义选择，后续如有需要可增加“保留手工修改”或“仅推荐不覆盖”的交互

### 下一步建议

1. 在“业务规则与活动”中增加场景标签或场景归属字段，减少仅靠关键词匹配的模糊性。
2. 后续把场景模板下沉为后台可配置能力，而不是只在代码中内置。
