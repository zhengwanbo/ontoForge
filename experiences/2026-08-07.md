## Guide 的 LLM 自由生成分析确认展示修正

### 背景
- Guide 在选择“LLM 自由生成 + 通用规则”后，会生成实体和关系建议，但第 2 步“分析确认”没有可见内容。
- 根因是该模式不产出结构化领域的 `document_facts`、`rule_analysis`、`schema_analysis`；页面也仅以这些字段决定能否进入第 2 步。

### 改动文件列表
- `frontend/src/views/ontology/OntologyBuild.vue`
- `experiences/2026-08-07.md`

### 具体改动
- 根据蓝图的 `generation_strategy === 'llm_first'` 识别 LLM 自由生成模式。
- 该模式完成生成或重新加载最新蓝图后，允许自动进入第 2 步，不再依赖结构化领域分析字段。
- 第 2 步增加通用业务范围确认视图，展示通用规则目标、MVP 范围与范围说明、已读取源表、建议实体/关系数量、首期对象、延后项和实施说明。
- 保留结构化领域生成原有的分析确认展示，不改变其字段和流程。

### 验证结果
- `cd frontend && npm run build` 通过（`vue-tsc` 类型检查与 Vite 生产构建均成功）。
- `git diff --check` 通过。

### 遗留问题与下一步建议
- 仍需在实际页面以“LLM 自由生成 + 通用规则”执行一次，确认模型返回的范围说明、延后项在当前数据源下符合业务预期。

## 自动修复历史重复边表名

### 背景
- 保存“调拨至”关系实现时报错：`ONTO_EDGE_OUTBOUNDORDER_REL_OUTBOUNDORDER_WAREHOUSE_WAREHOUSE` 已被关系“调拨至”使用。
- Oracle 实测确认根因是历史数据冲突：不同关系“调拨至”和“从出库”拥有同一个边表名；前者保存时被唯一性校验拦截。

### 改动文件列表
- `backend/app/api/mapping.py`
- `experiences/2026-08-07.md`

### 具体改动
- 当自动生成的边表名已被同分析域另一条关系占用时，系统保留原名称并追加当前关系 ID 的稳定后缀，生成唯一的 Oracle 边表名。
- 若追加后仍冲突，才提示用户手工修改名称；避免掩盖极低概率的二次碰撞。
- 用户重新保存“调拨至”即可修复该历史记录；“从出库”现有边表名不变。

### 验证结果
- `cd backend && python -m unittest tests.test_mapping_oracle_graph && python -m py_compile app/api/mapping.py` 通过（5 tests）。

## 管理页回填最新全域映射的关系建议
