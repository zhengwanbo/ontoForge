## 1. Guide 应用生成结果改为直接应用当前预览，并优化落库性能
### 背景
- 用户指出 `Guide 自动生成业务实体与关系` 中点击“应用生成结果”特别慢。
- 排查确认，慢的主要原因有两段：
  - 前端点击“应用生成结果”时，实际会再次执行整套 Guide 生成流程，然后才 `auto_apply`
  - 后端 `apply_blueprint()` 在同一请求内做同步串行落库，且存在逐实体 `flush()` 与属性懒加载带来的额外 ORM 往返

### 改动文件列表
- `backend/app/schemas/schemas.py`
- `backend/app/api/ontology.py`
- `backend/app/services/ontology_guide_service.py`
- `frontend/src/api/index.ts`
- `frontend/src/views/ontology/OntologyBuild.vue`
- `experiences/2026-07-28.md`

### 具体改动
- 新增“直接应用当前 Guide 预览”的后端接口：
  - `POST /domains/{domain_id}/guide/apply`
  - 请求体新增 `OntologyGuideApplyRequest`
  - 前端将当前 `guidePreview.entities / guidePreview.relations` 直接提交给该接口
  - 不再重新调用 `guide/generate`
- 前端按钮行为改造：
  - `applyOntologyGuide()` 不再执行 `generateOntologyGuide(true)`
  - 改为直接调用 `graphApi.applyOntologyGuide()`
  - 成功后只更新：
    - `guidePreview.apply_result`
    - `guidePreview.blueprint_status = 'APPLIED'`
    - 再执行一次 `loadGraphData()` 刷新图谱
- 后端 `apply_blueprint()` 落库路径优化：
  - 预加载当前分析域实体及其属性：
    - `selectinload(SysOntologyEntity.properties)`
  - 删除新实体创建后的逐条 `self.db.flush()`
  - 使用内存中的 `property_index` 和 `existing_props` 维护属性索引，避免通过懒加载反复触发查询
  - 去掉实体处理与关系处理之间额外的 `flush()`
  - 继续维持单次 `commit()` 的最终提交语义
- 新增 `mark_blueprint_status()`：
  - 当前预览应用成功后，把对应 `blueprint_id` 的状态更新为 `APPLIED`

### 验证结果
- 执行：
  - `./.venv311/bin/python -m py_compile app/api/ontology.py app/schemas/schemas.py app/services/ontology_guide_service.py`
  - `npm run build`
- 结果：
  - 后端语法检查通过
  - 前端构建通过

### 结论
- “应用生成结果”已从“重新生成 + 应用”改为“直接应用当前预览 + 刷图”，最重的一段重复生成已被去掉。
- `apply_blueprint()` 也已减少懒加载和中间 flush，数据库往返次数显著下降；后续体感耗时应明显缩短。

## 2. DDL 生成改为源数据驱动，不再生成空壳本体表/关系表
### 背景
- 用户要求在 `DDL生成与应用` 时，生成的本体表中的数据、关系表中的数据必须来源于源数据表，不能只是创建空的本体对象结构。
- 参考脚本：
  - `/Users/wanzheng/src/gwgx_src/oracle_graph_build/sql/10_pdx25_tams_agent_graph_build.sql`
  其核心做法是：
  - 通过 `CREATE TABLE ... AS SELECT ... FROM 源表` 生成实体对象数据
  - 通过 `edge_sql / 源表 JOIN` 生成关系边数据
  - 再基于这些有数据的表构建 Property Graph
- 排查现有实现发现两个关键问题：
  - `TABLE` 类型实体之前生成的是空壳 `CREATE TABLE (...)`
  - `关系表` 之前只有 `MANY_TO_MANY` 情况下才生成结构表，且不带源数据
  - `VIEW` 类型实体虽尝试基于映射拼 SQL，但多表场景没有有效 `JOIN ON`，并不可靠

### 改动文件列表
- `backend/app/api/ddl.py`
- `backend/app/services/ddl_service.py`
- `experiences/2026-07-28.md`

### 具体改动
- DDL 生成主策略调整：
  - `generate_ddl()` 现在先生成确定性的“源数据驱动 DDL”
  - 再将 LLM 产出的 DDL 作为补充合并，而不是让 LLM 主导实体/关系存储对象
  - 这样实体表、关系表的核心建模方式由后端映射规则确定，避免 LLM 继续产出空壳建表
- API 查询优化与约束：
  - `ddl.generate` 中对实体查询增加：
    - `properties`
    - `properties.mapping`
    - `entity_mapping`
  - 对关系查询增加：
    - `relation_mapping`
  - 同时对 `DDLService.generate_ddl()` 抛出的 `ValueError` 转为 `400` 返回
- 实体 DDL 改为源数据驱动：
  - `TABLE` 类型实体：
    - 改为 `CREATE TABLE ... AS SELECT ... FROM 源表/映射SQL`
    - 若存在主键属性，再追加 `ALTER TABLE ... ADD CONSTRAINT PK_...`
  - `VIEW` 类型实体：
    - 改为 `CREATE OR REPLACE VIEW ... AS <源数据查询>`
- 新增 `_build_entity_source_query()`：
  - 若 `entity_mapping.view_sql` 已维护，则直接使用该 SQL
  - 否则尝试根据属性映射自动拼装单表 `SELECT`
  - 支持：
    - `DIRECT`
    - `COMPUTED`
  - 若实体属性映射跨多个源表，且没有维护 `entity_mapping.view_sql`，则直接报错，要求先在数据映射中补充实体级 SQL，而不是继续生成错误或空壳 DDL
  - 若实体没有已确认的源数据映射，也直接报错
- 关系表 DDL 改为源数据驱动：
  - `_generate_relation_table_ddl()` 不再生成空结构关系表
  - 现在优先使用 `relation_mapping.edge_sql`
  - 生成：
    - `CREATE TABLE <关系存储名> AS SELECT edge_data.*, RELATION_NAME, RELATION_DESC FROM (<edge_sql>) edge_data`
  - 没有 `edge_sql` 的关系，不再生成空关系表
- Property Graph 边引用调整：
  - 当关系已有 `edge_sql` 时，Property Graph 现在引用对应的关系表，而不是引用额外生成的 edge view
  - `_generate_semantic_layer_ddl()` 中也不再默认附加 `_generate_relation_edge_view_ddls(relations)` 产生的关系边视图
- 新增 `_resolve_relation_storage_name()`：
  - 优先使用已有 `relation_table_name`
  - 否则按关系名生成稳定的 `ONTO_EDGE_*` 关系存储表名

### 验证结果
- 执行：
  - `./.venv311/bin/python -m py_compile app/api/ddl.py app/services/ddl_service.py`
  - `npm run build`
- 结果：
  - 后端语法检查通过
  - 前端构建通过

### 结论
- 当前 DDL 生成逻辑已从“创建本体对象结构”调整为“优先根据映射生成来源于源数据表的实体表/视图和关系表”。
- 若实体或关系还没有足够的源数据映射信息，系统现在会直接报错要求先补映射，而不是继续生成空壳 DDL。

## 7. Guide 支持“规则数据优先、无规则时通用回退”的本体生成

- 用户指出：对于类似 `SPEC_LIMIT` 这类带具体规则数据的分析域，当前 Guide 只看到了“有规则表结构”，却没有真正解析具体规则内容，因此生成出的本体对象与关系偏通用，无法准确体现缺陷识别范围、规则判定链路和根因分析对象。
- 期望行为调整为：
  - 如果分析域中存在像 `SPEC_LIMIT` 这类带具体规则数据的输入，并且能明确指出缺陷识别范围和缺陷识别数据，则优先解析这些规则数据，作为本体构建依据。
  - 如果没有这种规则数据提示，则继续沿用之前的通用本体构建方式。

  - 调用 `generateOntologyGuide` 时，将 `rule_datasets` 一并传给后端
  - Guide 预览补充展示：

## 8. Guide 输入规则细化：数据库模式可单独指定规则表，DDL 模式继续上传规则文件
### 背景
