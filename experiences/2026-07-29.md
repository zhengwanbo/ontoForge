## 7. 修复中文关系名导致 DDL 边表重名
### 背景
- DDL 历史显示生成脚本中重复出现 `CREATE TABLE ONTO_EDGE_EDGE AS`，执行时造成大量对象与约束重名失败。
- 排查确认关系存储名原先只保留英文、数字和下划线；中文关系名（如“属于”“产生观测”）被清洗为空后都回退为 `EDGE`，使多条关系共享同一边表名。

### 改动文件列表
- `backend/app/services/ddl_service.py`
- `backend/tests/test_ontology_graph_mapping_design.py`
- `experiences/2026-07-29.md`

### 具体改动
- 未配置 `relation_table_name` 时，边表名改为 `ONTO_EDGE_<关系名标识>_<关系ID>`。
- 当关系名是中文或其他非 ASCII 文本时，名称形如 `ONTO_EDGE_EDGE_REL_111AAA`，关系 ID 保证同一分析域内的边表唯一。
- 已明确配置的 `relation_table_name` 仍优先使用，仅统一转换为大写。
- 新增回归测试，覆盖两条中文关系名生成不同边表名的情形。

### 验证结果
- 执行：
  - `python -m unittest tests.test_ontology_graph_mapping_design -v`
  - `python -m py_compile app/services/ddl_service.py tests/test_ontology_graph_mapping_design.py`
- 结果：
  - 6 个单元测试全部通过。
  - 后端生成服务与测试文件语法检查通过。

### 结论
- 重新生成 DDL 后，不再会把所有中文关系默认生成到 `ONTO_EDGE_EDGE`。

## 3. DDL 页面改为单接口聚合加载，减少打开时的 N+1 请求
### 背景
- 用户反馈 `DDL生成与应用` 页面在打开时明显偏慢，并确认当前慢点主要发生在页面初始化阶段，而不是生成 DDL 或执行 DDL。
- 排查前端实现确认，原逻辑会先请求实体列表、关系列表、最新 blueprint，再对每个实体继续请求属性列表和 `entity_mapping`，对每个关系继续请求 `relation_mapping`，形成明显的前端 N+1 请求链路。

### 改动文件列表
- `backend/app/api/ddl.py`
- `frontend/src/api/index.ts`
- `frontend/src/views/ddl/DDLManage.vue`
- `experiences/2026-07-29.md`

### 具体改动
- 后端新增聚合接口：
  - `GET /ddl/domains/{domain_id}/context`
  - 一次性返回：
    - 实体列表
    - 每个实体的属性列表及属性映射
    - 每个实体的 `entity_mapping`
    - 关系列表及 `relation_mapping`
    - 最新 blueprint 摘要载荷
- 查询策略调整：
  - 实体查询使用 `selectinload(SysOntologyEntity.properties).selectinload(SysOntologyProperty.mapping)`
  - 同时预加载 `SysOntologyEntity.entity_mapping`
  - 关系查询预加载 `SysOntologyRelation.relation_mapping`
  - 这样页面初始化时只需一次接口调用，由后端集中取数并序列化返回
- 前端 DDL 页面切换到聚合接口：
  - `ddlApi` 新增 `getContext(domainId)`
  - `DDLManage.vue` 的 `reloadDomainContext()` 删除原来的多轮 `entityApi / relationApi / propertyApi / mappingApi` 串并行请求
  - 改为单次调用 `ddlApi.getContext()`

### 验证结果
- 执行：
  - `python -m py_compile backend/app/api/ddl.py`
  - `npm run build`
- 结果：
  - 后端语法检查通过
  - 前端构建通过

### 参考脚本模式分析
- 参考脚本的核心不是“一个本体对象直接映射一张原始表”，而是分三层落地：

  - `TAMS_PRODUCT_LOT`：按批次聚合形成派生节点
  - `TAMS_PROCESS_EVENT`：从宽表的多个工站字段展开为事件节点，并生成稳定 `EVENT_ID`
- 典型边模式：
  - 边 ID 由源节点 KEY、关系名和目标节点 KEY 拼接
  - 边表保留业务关系属性
  - 每张边表增加 `PRIMARY KEY (EDGE_ID)`
- Oracle 26ai 校验依据：
  - 顶点需要稳定 KEY
  - 边需要自身 KEY
  - SOURCE KEY / DESTINATION KEY 必须引用两端顶点 KEY

## 26. Oracle 重建清理缺失对象不再计为 DDL 失败

### 背景
- 用户重新生成并执行 DDL 后，失败数由 35 条降至 5 条。
- 对目标 Oracle 只读核查确认，13 张 `ONTO_NODE_*` 节点表、16 张 `ONTO_EDGE_*` 边表及 `SFR_PG` 均已成功创建，因此 5 条并非建表或建图失败。
- 根因是重建脚本先清理历史对象；首次部署或前次不完整部署时，部分待清理对象本来不存在。Oracle 不支持 `DROP ... IF EXISTS`，若执行器未在执行前识别缺失对象，就会将该清理行为统计为失败。

### 改动文件列表
- `backend/app/services/ddl_service.py`
- `backend/tests/test_ontology_graph_mapping_design.py`
- `experiences/2026-07-29.md`

### 具体改动
- DDL 执行器在执行 `DROP TABLE`、`DROP VIEW`、`DROP PROPERTY GRAPH` 前，先通过 `USER_OBJECTS` 查询目标对象是否存在。

- 对表、视图、属性图统一支持创建和删除语句的对象识别。
- 诊断期间曾删除 `SFR_PG` 以验证 Oracle 的隐式提交行为，已立即使用当前已部署节点/边表成功重建，未修改任何节点或边数据。
