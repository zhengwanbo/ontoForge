## 背景
- 本次需求针对“源数据浏览管理”页面，要求不再只浏览本地 SQLite 示例表，而是能够直接选择“系统管理 -> 数据源管理”中配置的数据库连接。
- 用户需要在页面中完成以下链路：选择数据库连接 -> 选择 schema -> 通过表名前缀过滤浏览表 -> 选择表后查看字段名、类型、缺省值、描述 -> 查看前 10 行示例数据。
- 仓库中原有能力分散在两处：`frontend/src/views/source/SourceData.vue` 仍基于本地 `/source/tables` 接口浏览 SQLite 表；`backend/app/api/datasource.py` 里已经有 Oracle 数据源的测试连接、列表示例表和查字段接口，但没有接入源数据浏览主页面，也没有统一提供 schema 列表和前 10 行示例数据。

## 具体改动

### 1. 后端 source 模块扩展为外部数据源浏览入口
- 在 `backend/app/api/source_data.py` 中新增接口：
  - `GET /api/v1/source/datasources`：返回可用于浏览的已启用数据源列表。
  - `GET /api/v1/source/datasources/{source_id}/schemas`：返回当前连接可见的 schema 列表、默认 schema 和当前连接用户。
  - `GET /api/v1/source/datasources/{source_id}/tables`：按 schema 和前缀过滤查询表列表。
  - `GET /api/v1/source/datasources/{source_id}/tables/{table_name}/detail`：返回字段结构、表描述和样例数据。
- 保留原 `/source/tables`、`/source/tables/{table}/columns` 等本地 SQLite 相关接口，避免影响其他模块或后续兼容需求。

### 2. 在 `SourceDataService` 中补齐 Oracle 浏览逻辑
- 新增数据源列表查询逻辑，从 `sys_data_source` 中提取已启用连接，供源数据页面选择。
- 新增 schema 列表查询逻辑，优先读取 `ALL_USERS`，并确保配置 schema、用户名 schema、当前连接用户 schema 会被纳入候选项。
- 新增按 schema + 前缀查询表列表逻辑，基于 `ALL_TABLES` 和 `ALL_TAB_COMMENTS` 返回表名、描述、估算行数。
- 新增表详情查询逻辑：
  - 基于 `ALL_TAB_COLUMNS`、`ALL_COL_COMMENTS` 返回字段名、类型、是否可空、缺省值、描述。
  - 基于 `ALL_TAB_COMMENTS` 返回表描述。
  - 直接查询目标表，返回前 10 行示例数据。
- 新增值归一化逻辑，处理 `datetime`、`date`、`Decimal`、`bytes` 等类型，避免前端 JSON 序列化问题。

### 3. 前端源数据页面重构
- 用新的 `frontend/src/views/source/SourceData.vue` 替换旧实现，页面改为四段式浏览：
  - 顶部工具区：数据库连接选择、schema 选择、表名前缀过滤、刷新。
  - 左侧表列表：展示表名、所属 schema、表描述、行数。
  - 右侧表头信息：表名、schema、字段数、样例行数、表描述。
  - 右侧明细区：字段结构表 + 前 10 行样例数据表。
- 在 `frontend/src/api/index.ts` 中补充 `sourceApi` 新方法，统一调用新的 source 浏览接口。

## 遗留问题
- 当前外部数据源浏览实现面向 Oracle 数据源，和系统管理页面的现有实现保持一致；如果后续要支持 MySQL、PostgreSQL，需要在 `SourceDataService` 中继续抽象不同数据库方言。
- 前 10 行样例数据目前按 `SELECT * ... FETCH FIRST 10 ROWS ONLY` 返回，不保证业务排序；如果后续需要“最新 10 行”或按主键排序，需要补充排序策略。
- 表行数来自 Oracle `ALL_TABLES.NUM_ROWS`，这通常是统计信息值，不一定与实时 `COUNT(*)` 一致。

## 下一步建议

- 更新配置时，如果修改了 `api_base_url` 或 `model_name`，也会重新按当前地址做归一化，避免“旧前缀 + 新直连地址”继续存入库中。

- 在 `frontend/src/views/system/SystemManage.vue` 中把模型名称输入框占位提示从 `deepseek-chat` 调整为 `deepseek-v4-flash`，减少误填旧模型名或不兼容模型名的概率。

- 用户进一步反馈，本体图中的边箭头不应该始终固定连到目标节点“最左侧中点”。只要箭头方向明确指向目标节点即可；如果箭头顶点压在节点边框甚至节点内部，节点会把箭头遮住，反而看不出方向。
- 现状中普通关系边使用固定端点：
  - 起点：源节点中心偏右
  - 终点：目标节点左侧中点
- 这种做法只适合“从左往右”的简单布局，一旦节点上下分布或斜向分布，箭头就容易被节点遮挡。

## 具体改动

### 1. 普通关系边改为按方向动态计算锚点
- 在 `frontend/src/views/ontology/OntologyBuild.vue` 中新增几何辅助方法：
  - `getNodeCenter(nodeId)`：获取节点中心点。
  - `getNodeBoundaryPoint(from, to, gap)`：根据连线方向，求连线从节点中心出发与节点外接矩形边界的交点。
  - `getGraphEdgeGeometry(edge)`：统一返回一条边的起点、终点和标签中点。
- 结果是：
  - 边的起点不再固定写死，而是根据源节点到目标节点的方向落在源节点外轮廓上。
  - 边的终点也不再固定钉在目标节点左中点，而是落在目标节点“朝向源节点的那一侧”。

### 2. 目标箭头额外留出外侧间距，避免被节点遮挡
- 在终点几何计算时引入 `graphArrowGap = 12` 的外侧间距。
- 箭头并不是压在线的终点刚好贴着节点边缘，而是停在目标节点外轮廓外一点点的位置。
- 这样箭头仍然明确指向目标节点，但箭头头部会保持可见，不会被节点矩形盖住。

### 3. 边标签位置同步改为跟随真实边中点
- 关系名称标签的白底矩形和文本位置改为使用 `getGraphEdgeGeometry(edge).mid`。
- 避免在边锚点动态变化后，标签仍然按照旧的“左右中点平均值”计算，导致文字和线条脱节。

  - 给节点补齐 `typeName` 和默认 `config`；
  - 过滤掉引用不存在节点的脏边。
- 这样即使历史流程图里已经因为旧 bug 留下了重复 ID，进入编辑器时也会被尽量自动修正，避免继续污染当前操作。

### 3. 新建流程图时显式重置计数器
- 在 `createProcess()` 中创建默认开始/结束节点前，先显式把 `flowIdCounter = 0`。
- 确保一个全新流程图的起始编号稳定，而已有流程图则按当前节点最大编号继续递增，两个路径分开处理，避免状态串扰。

  - 结果：通过。

## 遗留问题

## 背景
- 用户要求调整“数据映射”页面的 LLM 自动映射能力：
  - 在选择业务实体后，点击 `LLM自动映射` 时，不再只对现有本体属性做字段推荐；
  - 而是要让 LLM 读取当前分析上下文里的数据库连接对象，结合表描述、字段信息和样例数据，识别与该业务实体最相关的源字段；
  - 将这些字段作为该业务实体的属性候选，并记录每个属性来自哪个原始表和字段；
  - 点击“确认映射”后，再把这些属性与来源映射正式写入本体对象。
- 原实现存在两个核心缺口：
  - 后端自动映射读取的是本地 SQLite 示例表 `get_tables_metadata()`，不是系统配置的数据源；
  - 自动映射只会给“实体已有属性”写入 `sys_property_mapping` 建议，无法支持“新增属性候选后确认落库”。

## 具体改动

### 1. 自动映射请求扩展为“实体 + 数据源 + Schema”上下文
- 在 `AutoMappingRequest` 中新增：
  - `source_id`
  - `schema`
  - `max_tables`
  - `sample_limit`
- 这样数据映射页在触发自动映射时，可以明确告诉后端应该读取哪个数据源、哪个 Schema，而不是继续使用本地示例表。

### 2. SourceDataService 增加远程表元数据聚合能力
- 在 `backend/app/services/source_data_service.py` 中新增：
  - `get_remote_tables_metadata_for_mapping()`
  - `_get_default_data_source()`
  - `_rank_tables_for_mapping()`
  - `build_entity_keywords()`
- 具体行为：
  - 先根据传入的 `source_id`，或系统默认启用数据源，定位本次自动映射应使用的连接；
  - 读取该数据源指定 Schema 下的表列表；
  - 根据实体名、显示名、实体描述提取关键词，对候选表做相关性排序；
  - 只取前若干张最相关的表，再逐张拉取字段结构、字段注释和少量样例数据，作为 LLM 提示词输入。
- 这样自动映射不再基于“本地假数据”，而是真正读取外部 Oracle 数据源元数据。

### 3. LLM 自动映射从“现有属性匹配”升级为“属性候选生成 + 来源字段推荐”
- 在 `backend/app/services/llm_service.py` 中重写自动映射提示词和返回归一化逻辑。
- 新的自动映射输出不再只包含：
  - `sourceTable`
  - `sourceColumn`
- 而是扩展为完整候选结构：
  - `propertyName`
  - `propertyDisplayName`
  - `propertyDesc`
  - `matchedPropertyId`
  - `matchedPropertyName`
  - `sourceTable`
  - `sourceColumn`
  - `sourceDataType`
  - `mappingType`
  - `confidence`
  - `reason`
  - `formula`
- 规则是：
  - 如果当前本体里已有对应属性，优先返回 `matchedPropertyId / matchedPropertyName`；
  - 如果源字段明显相关但当前本体里没有，则直接返回“新增属性候选”。
- 同时保留了回退逻辑：如果 LLM 没有返回可解析 JSON，就按字段名和注释生成一批基础候选，避免页面完全无结果。

### 4. 自动映射接口改为返回候选，不再提前落库
- `backend/app/api/mapping.py` 中的 `/entities/{entity_id}/auto-mapping` 调整为：
  - 读取远程数据源元数据；
  - 调用 LLM 返回属性候选和来源字段建议；
  - 直接把候选结果返回前端；
  - 不再像旧逻辑那样在自动映射阶段就立刻写 `sys_property_mapping`。
- 这样“自动映射”变成真正的“建议生成”，而“确认映射”才负责正式写库，更符合用户要求。

### 5. 确认映射接口补齐“新增属性 + 映射落库”闭环
- `backend/app/api/mapping.py` 中的 `/entities/{entity_id}/mappings/confirm` 逻辑增强为：
  - 如果是已有属性：
    - 更新或创建 `sys_property_mapping`
    - 写入来源表、来源字段、映射类型、置信度、理由等
  - 如果是 LLM 新增属性候选：
    - 先在 `sys_ontology_property` 中创建新属性
    - 再创建对应 `sys_property_mapping`
  - 确认成功后：
    - 将属性 `source_mark` 置为 `MAPPED`
    - 将实体映射状态置为 `CONFIRMED`
    - 将实体状态置为 `MAPPED`
- 同时补了一个细节：
  - 当某行被用户拒绝时，如果已经有旧映射，会把该属性的 `source_mark` 回退为 `PENDING`，避免图上仍显示为已映射。

### 6. 数据映射页面重构为“分析域 + 实体 + 数据源 + Schema”四级上下文
- `frontend/src/views/mapping/DataMapping.vue` 改为顶部四个选择器：
  - 分析域
  - 实体
  - 数据库连接
  - Schema
- 页面初始化时：
  - 默认读取系统中的启用数据源；
  - 优先选默认数据源；
  - 自动拉取该数据源的 Schema 和候选表。
- 手工映射下拉框也改为使用远程数据源表列表和字段列表，不再使用本地 `/source/tables` 的 SQLite 示例表。

### 7. 前端支持展示和确认 LLM 新增属性候选
- 映射表格新增“属性来源”标识：
  - `已有属性`
  - `LLM新增候选`
- 点击 `LLM自动映射` 后：
  - 前端会调用新的自动映射接口；
  - 把候选结果合并到当前表格中；
  - 已有属性的行会被更新来源字段和理由；
  - 新候选属性则追加到列表中，允许用户直接编辑属性名、显示名、说明、来源表、来源字段。
- 点击 `确认映射` 时：
  - 前端不再只传 `mapping_id + action`；
  - 而是把整行属性候选、来源表字段、映射类型、说明、置信度等完整提交给后端；
  - 由后端统一完成“已有属性更新”或“新增属性创建”。

### 8. 页面交互顺手做了两点收口
- 数据映射页切换分析域时，会同步更新 Pinia 中的当前分析域，避免切到其他页面上下文漂移。
- 属性表里的手工调整不再每改一格就立刻写库，而是统一在“确认映射”时一次提交，这样才能兼容“新增属性候选”的暂存状态。
