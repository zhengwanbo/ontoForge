# 2026-07-15

## 背景
- 用户反馈系统当前无法登录，怀疑与刚刚调整登录页文案有关。
- 本次登录页改动仅删除了静态提示文案，因此需要沿登录链路核对前端提交、后端鉴权和实际数据库中的管理员账号状态。

## 排查范围
- `frontend/src/views/Login.vue`
- `frontend/src/api/index.ts`
- `backend/app/api/system.py`
- `backend/app/main.py`
- `backend/app/core/security.py`
- Oracle 开发库 `sys_user`

## 排查结论
- 登录页前端提交逻辑未被本次文案调整破坏，`handleLogin`、`authApi.login` 和 `/api/v1/system/auth/login` 调用链保持正常。
- 项目当前实际使用的是 `backend/.env` 中配置的 Oracle 数据库：
  - `oracle+oracledb://oonbuild:***@163.192.218.148:1521/?service_name=orclpdb1`
- 仓库中的 `backend/ontology_platform.db` 为 0 字节空文件，当前并非系统运行时使用的数据源。
- Oracle 库中 `sys_user` 仅存在 1 个账号：
  - `username = admin`
  - `status = ACTIVE`
- 该账号原有密码哈希不再匹配 `admin123`，因此登录失败的真实原因是开发环境管理员密码已被修改，而不是登录页展示文案调整导致。

## 处理动作
- 通过项目 Python 环境连接 Oracle，将现有 `admin` 账号密码重置为开发默认密码 `admin123`。
- 未改动登录接口代码，仅修复当前开发库中的管理员凭据。

## 验证结果
- 直接校验密码哈希：
  - `verify_password('admin123', user.password_hash)` 返回 `True`。
- 使用 FastAPI `TestClient` 调用登录接口：
  - `POST /api/v1/system/auth/login`
  - 请求体：`{"username":"admin","password":"admin123"}`
  - 返回：HTTP 200
- 结论：当前可使用 `admin / admin123` 正常登录。

## 遗留问题
- 由于前端已按要求移除了默认账号提示，当前默认管理员仍然存在，但不会在界面中展示。
- 当前开发环境只有一个 `admin` 账号，且密码可能被人工修改；如果再次发生类似情况，界面侧不会给出任何可见提示。

## 下一步建议
- 如果希望继续保留“开发默认管理员”，建议补一个受配置开关控制的初始化策略，只在显式开启时重置或创建默认管理员。
- 如果希望彻底避免默认账号依赖，建议增加首次启动时的管理员初始化流程，而不是把固定密码长期保留在数据库初始化逻辑中。

## 背景
- 用户反馈 `GET /api/v1/mapping/entities/{entity_id}/mappings` 返回 500。
- Oracle 报错为 `ORA-00904: "SYS_PROPERTY_MAPPING"."ENTITY_ID": invalid identifier`，说明代码仍按 `sys_property_mapping.entity_id` 查询，但当前 Oracle 实表已经没有这列。

## 改动文件列表
- `backend/app/models/models.py`
- `backend/app/api/mapping.py`
- `experiences/2026-07-15.md`

## 具体改动

### 1. 修正属性映射 ORM 模型
- 在 `backend/app/models/models.py` 中移除 `SysPropertyMapping.entity_id` 列映射。
- 同时移除 `SysOntologyEntity.property_mappings` 与 `SysPropertyMapping.entity` 这组依赖错误外键的关系定义，避免 ORM 自动生成带坏列的 SQL。

### 2. 属性映射列表改为通过属性表反查实体
- 在 `backend/app/api/mapping.py` 的 `get_property_mappings` 中，不再使用：
  - `SysPropertyMapping.entity_id == entity_id`
- 改为：
  - `sys_property_mapping` 通过 `property_id` 关联 `sys_ontology_property`
  - 再按 `sys_ontology_property.entity_id` 过滤
- 返回结果里的 `entity_id` 也改为使用关联出来的 `sys_ontology_property.entity_id`，保持前端返回格式不变。

### 3. 创建属性映射时不再写入不存在的列
- 在 `update_property_mapping` 和 `confirm_mappings` 的“新建 `SysPropertyMapping`”分支中，去掉对 `entity_id` 的赋值。
- 这样即使没有既有属性映射记录，也能按当前 Oracle 实表结构正常插入。

## 下一步建议
- 建议补一轮 Oracle 实表与 SQLAlchemy 模型的结构对齐检查，至少覆盖：

  - `当前运行环境未安装 pypdf，暂时无法解析 PDF 文档`
- 避免再次出现“ImportError 直接冒泡成 500”的问题。
